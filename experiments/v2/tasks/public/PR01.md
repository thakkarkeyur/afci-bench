## Objective

Order totals must be exact to the cent even when line items carry fractional unit
prices. Ensure the subtotals and totals the service returns are correct.

## User-visible behaviour

When an order is created, every line item's `subtotal` and the order's `total` are
monetary amounts rounded to exactly two decimal places, with no sub-cent drift.

For example, an order with three line items whose `unitPrice` values are `0.10`,
`0.10` and `0.70`, each with `quantity` `1`, returns line-item subtotals `0.10`,
`0.10` and `0.70`, and a `total` of exactly `0.90`. Today that same order returns
a `total` of `0.8999999999999999`.

## Inputs and outputs

- Input: the existing create-order request; no new request fields.
- Output: the existing create-order response, with every `subtotal` and the
  `total` rounded to exactly two decimal places.

## Constraints

- Every monetary amount the service returns is rounded to exactly two decimal
  places.
- Adding more line items must not accumulate sub-cent error in `total`.
- `total` and `subtotal` remain JSON numbers, and the existing response keys are
  unchanged.
- How the amounts are represented or rounded inside the service is not
  constrained.
- Existing endpoints keep their current behaviour and responses unchanged.

## Functional completion criteria

- An order with `unitPrice` values `0.10`, `0.10` and `0.70`, each with `quantity`
  `1`, returns a `total` of exactly `0.90`.
- Orders whose line items sum with sub-cent drift today return a `total` rounded
  to exactly two decimal places.
- Orders that already return exact totals keep them: a single line item with
  `quantity` `3` at `unitPrice` `15.33` still returns a `subtotal` and `total` of
  `45.99`.

## Validation

Run `npm run ci:agent`; it must pass.
