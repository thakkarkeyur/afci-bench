## Objective

Order creation already writes one structured request-log record per request, but
that record does not describe the HTTP call that produced it, and a rejected
order-creation request produces no structured error-log record at all. Complete
the structured logging for order creation.

## User-visible behaviour

- Every `POST /orders` request, accepted or rejected, produces exactly one
  structured request-log record containing at least these keys:
  - `correlationId` — the request's correlation identifier: the value supplied
    with the request if there is one, otherwise a generated non-empty value;
  - `method` — the HTTP method, the string `"POST"`;
  - `path` — the request path, the string `"/orders"`;
  - `statusCode` — the numeric HTTP status code actually sent to the client, for
    example `201` or `400`;
  - `status` — the outcome: the string `"success"` for a 2xx response and the
    string `"fail"` otherwise;
  - `operation` — the operation name the service already records, unchanged;
  - `latencyMs` — the numeric duration the service already records, unchanged.
- Every `POST /orders` request that does not succeed additionally produces
  exactly one structured error-log record containing at least these keys:
  - `correlationId` — the same value as that request's request-log record;
  - `errorType` — a non-empty string naming the kind of failure. Its exact value
    is not fixed by this task; any non-empty string is acceptable.
  - `message` — a non-empty human-readable description of the failure.
- An error-log record must not expose a stack trace or a secret: it must have no
  `stack` key, and no key carrying a stack trace, credential or token.

## Inputs and outputs

- No change to the request bodies, response bodies, status codes or headers of any
  existing endpoint.
- The observable effect is the presence and completeness of the structured log
  records described above, written through the logging output the service already
  uses.

## Constraints

- Every key listed above is present and populated on the record it belongs to, and
  `statusCode` equals the status code actually sent to the client.
- Exactly one request-log record per `POST /orders` request, and exactly one
  error-log record per unsuccessful `POST /orders` request.
- Successful order creation is otherwise functionally unchanged, and the existing
  HTTP behaviour for invalid input and for server errors is unchanged.

## Functional completion criteria

- A successful create returns HTTP 201 and produces one request-log record with
  `method` `"POST"`, `path` `"/orders"`, `statusCode` `201`, `status`
  `"success"`, a non-empty `correlationId`, the existing `operation` value and a
  numeric `latencyMs`, and produces no error-log record.
- A create rejected for invalid input returns HTTP 400 and produces one
  request-log record with `statusCode` `400` and `status` `"fail"`, plus exactly
  one error-log record with a non-empty `correlationId`, a non-empty `errorType`
  and a non-empty `message`, and with no `stack` key.
- A request that supplies its own correlation identifier produces log records
  carrying that same identifier; a request that supplies none produces log records
  carrying a generated non-empty identifier.

## Validation

Run `npm run ci:agent`; it must pass.
