## Objective

Order creation already emits a structured log record for each request and each
error. Read traffic does not. Make read traffic emit the same structured records.

## User-visible behaviour

- Every handled request to the health endpoint and to any order-read endpoint
  produces one structured request-log record containing: the request's
  correlation identifier, the operation being performed, the outcome (success or
  failure), and how long the request took.
- Every request that fails produces one structured error-log record containing:
  the correlation identifier, an error type, and a human-readable message.
- If a request arrives without a correlation identifier, a correlation identifier
  is generated and used consistently for that request's log records.

## Inputs and outputs

- No change to the request or response bodies of existing endpoints.
- The observable effect is the presence and completeness of the structured log
  records described above.

## Constraints

- The four request-log fields and the three error-log fields listed above must
  each be present and populated.
- Existing successful responses and status codes are unchanged.

## Functional completion criteria

- A successful read produces a request-log record with all four fields populated.
- A failing read produces both a request-log record (marked as a failure) and an
  error-log record with all three fields populated.
- A request without a supplied correlation identifier still results in log
  records carrying a non-empty correlation identifier.

## Validation

Run `npm run ci:agent`; it must pass.
