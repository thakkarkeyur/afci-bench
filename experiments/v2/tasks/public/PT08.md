## Objective

`POST /orders` creates an order and answers with that order's `total`. A caller
with a spending limit cannot state it: it finds out what the order costs only from
the response to the request that created it. Let a caller declare, on the request
itself, the highest total it is willing to accept, and answer a request whose total
is above that with a dedicated rejection response instead of the created-order
response.

## User-visible behaviour

`POST /orders` gains one **optional query parameter**, `maxTotal`. Nothing else
about the request changes: the request body stays exactly the existing
create-order request body, this task adds **no** request-body field, and it adds
**no** request header.

`maxTotal` declares the highest order total the caller will accept for that one
request. It is compared against the `total` the service already reports for that
same request — see **No new monetary rules** below.

Throughout this section, the worked example is the existing create-order request
body

```json
{
  "customerId": "cust-1",
  "items": [
    { "productId": "p-100", "name": "Notebook", "quantity": 2, "unitPrice": 25 }
  ]
}
```

for which the service today reports a line-item `subtotal` of `50` and a `total`
of `50`.

### 1. `maxTotal` is absent

A `POST /orders` request that carries no `maxTotal` behaves exactly as it does
today — the same status codes, the same response bodies and the same values. No
maximum is applied.

### 2. `maxTotal` is present once and well formed

A `maxTotal` value is **well formed** when it is written as either

- one or more decimal digits — for example `0`, `25`, `50`, `1000`; or
- one or more decimal digits, a single `.`, then one or more decimal digits — for
  example `0.00`, `25.50`, `61.32`.

A well-formed value is a finite, non-negative number in ordinary base-10 notation.
`0` is well formed: a maximum of zero is a legitimate maximum, and it is **not**
treated as an absent parameter.

For a well-formed `maxTotal`, writing `T` for the `total` the service reports for
that request:

| Comparison | Answer |
|---|---|
| `T` is less than `maxTotal` | ordinary order creation, unchanged |
| `T` equals `maxTotal` | ordinary order creation, unchanged |
| `T` is greater than `maxTotal` | HTTP 409 and the body under **A total above the maximum** |

**The maximum is inclusive.** A total exactly equal to `maxTotal` is accepted: the
worked example above with `?maxTotal=50` answers HTTP 201 with the ordinary
created-order response body, and equality is never a rejection.

### 3. `maxTotal` is present and not well formed

Each of the following is rejected with HTTP 400 and the body under **A `maxTotal`
that is not well formed**:

- a value beginning with a minus sign — for example `-1`, `-0.01`;
- an **empty** value: `?maxTotal=` carries a `maxTotal` that is present and empty,
  and an empty value is **not** an absent parameter;
- a value that is not a numeral at all — for example `abc`, `12abc`, `--`;
- any spelling of `NaN` or of `Infinity`, in any combination of upper- and
  lower-case letters and with or without a leading sign — for example `NaN`, `nan`,
  `NAN`, `Infinity`, `infinity`, `-Infinity`.

### 4. `maxTotal` is given more than once

A request that carries `maxTotal` more than once — for example
`?maxTotal=50&maxTotal=100` — is rejected with HTTP 400 and the same body under
**A `maxTotal` that is not well formed**. Such a request is ambiguous and is
answered as invalid; one of the repeated values must **never** be silently chosen
and applied.

### A total above the maximum

When `maxTotal` is well formed and the reported total is greater than it, the
request answers HTTP 409 with a JSON body containing exactly:

```json
{
  "error": "OrderValueLimitExceeded",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- `error` is exactly the string `OrderValueLimitExceeded`.
- `message` is a non-empty string. Its exact wording is not part of the required
  behaviour; any non-empty string satisfies it.
- `correlationId` is a non-empty string. This task fixes no further requirement on
  its value.
- The body carries **no** other key: exactly those three, and no fourth.

That answer is **not** interchangeable with a rejection for invalid input. A total
above the maximum is answered HTTP 409 with `error` exactly
`OrderValueLimitExceeded` — never HTTP 400, and never `error` `ValidationError`.

### A `maxTotal` that is not well formed

Every case in sections 3 and 4 answers HTTP 400 with the JSON body `POST /orders`
already answers a rejected create-order request with, containing exactly:

```json
{
  "error": "ValidationError",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- `error` is exactly the string `ValidationError`.
- `message` is a non-empty string, with its exact wording not part of the required
  behaviour.
- `correlationId` is a non-empty string.

This is the existing rejection body, reused unchanged. This task introduces **no**
second rejection shape for invalid input, adds no key to that body and removes
none.

### An invalid request body keeps the answer it already has

A `POST /orders` request whose body does not satisfy the existing create-order
input validation answers exactly as it does today — HTTP 400 with the
validation-error body above — whether `maxTotal` is absent, well formed, or not
well formed. In particular, when the body is invalid **and** `maxTotal` is not
well formed, the answer is the one the invalid body already produces on its own:
the ill-formed `maxTotal` does not change it, replace it or suppress it. The
existing input validation keeps the behaviour it already has, and this task
re-specifies none of it.

Both of those rejections carry HTTP 400 and `error` exactly `ValidationError`, so
what this requires is that such a request is still answered as invalid input in
that existing shape — never HTTP 409, and never a successful creation.

A total exists only for a request that satisfies that existing input validation,
so a maximum is only ever compared against a total the service actually reports. A
request rejected for an invalid body is therefore never answered HTTP 409.

### No new monetary rules

`maxTotal` is compared against the very `total` the service already computes and
reports for that request. This task introduces **no** new rounding rule, **no** new
monetary-precision rule, **no** discount rule and **no** currency conversion, and
it changes **no** line-item `subtotal` and **no** order `total`. `maxTotal` is
**not** rounded, re-scaled or converted before the comparison, and no new numeric
algorithm is defined anywhere.

## Inputs and outputs

- Input: the existing create-order request body, plus the optional query parameter
  `maxTotal`.
- Output when no maximum applies, or when the reported total is at or below it: the
  existing create-order response, unchanged — HTTP 201 with the existing body and
  the existing values.
- Output when the reported total is above the maximum: HTTP 409 with a JSON body
  whose keys are exactly `error`, `message` and `correlationId`, and whose `error`
  is exactly `OrderValueLimitExceeded`.
- Output when `maxTotal` is present and not well formed, or is given more than
  once: HTTP 400 with the existing validation-error body, whose `error` is exactly
  `ValidationError`.

## Error behaviour

- Two answers, and only two, are added by this task: HTTP 409 with `error`
  `OrderValueLimitExceeded` for a total above the maximum, and the existing HTTP
  400 `ValidationError` body for a `maxTotal` that is not well formed or is
  repeated.
- The two are never confused: a total above the maximum is never answered HTTP
  400, and an ill-formed or repeated `maxTotal` is never answered HTTP 409.
- No existing rejection of `POST /orders` gains a new status code or a new body.

## Out of scope

Everything below is **outside** this task. This task states no required status code
and no required response body for any of it, and the service's existing handling of
such a request is unchanged.

- **Spellings of `maxTotal` this task does not define.** Exponent notation such as
  `1e3`; hexadecimal such as `0x10`; an explicit leading plus such as `+5`; a value
  with no digit before the decimal point such as `.5`; a value with no digit after
  the decimal point such as `5.`; a minus sign in front of a zero, such as `-0` or
  `-0.00`; a value carrying leading or trailing whitespace, percent-encoded or
  otherwise; a digit-grouping separator such as `1,000`; the key written with no
  value part at all, as in `?maxTotal`; and any bracketed or structured spelling of
  the key, as in `?maxTotal[]=50`. Their treatment is deliberately left undefined:
  **no** particular status code and **no** particular response body is required for
  any of them. None of them is one of the cases in sections 2, 3 and 4, and where a
  spelling listed here could also be read as falling under section 3, this list
  governs and the spelling is out of scope.
- **Anything not visible in the answer to a single request.** Every requirement in
  this task is a status code and a JSON response body. It states nothing about what
  the service stores, or does not store, for a request answered HTTP 409 or HTTP
  400.
- **Transport-level and body-parsing rejections.** A body that cannot be parsed as
  JSON, a body that is too large, a request whose media type or charset is not
  supported, an aborted request, and every other transport-level rejection keep
  exactly the handling they have today.
- **Response headers.** No response header is part of this task's required
  behaviour. Any response header the service already sets keeps the behaviour it
  already has.
- **Log output.** Log output is not part of this task's required behaviour.
- **Other endpoints.** `GET /health` keeps its current behaviour, status code and
  response body. No other endpoint is added or changed.

## Functional completion criteria

Each criterion is decidable from the status code and the JSON body of the answers
to ordinary HTTP requests.

- **A.** A request with a valid body and no `maxTotal` answers HTTP 201 with the
  existing create-order response body and the existing values, exactly as it does
  today.
- **B.** The worked example (reported `total` `50`) sent with `?maxTotal=100`
  answers HTTP 201 with that same ordinary created-order body.
- **C.** The worked example sent with `?maxTotal=50` — the maximum exactly equal to
  the reported total — answers HTTP 201 with that same ordinary created-order body.
- **D.** The worked example sent with `?maxTotal=25` answers HTTP 409 with a JSON
  body whose keys are exactly `error`, `message` and `correlationId`, whose `error`
  is exactly `OrderValueLimitExceeded`, whose `message` is a non-empty string and
  whose `correlationId` is a non-empty string.
- **E.** The worked example sent with `?maxTotal=0` answers HTTP 409 with that same
  body, because its reported total is greater than `0`.
- **F.** An order whose reported total is exactly `0` — for example one whose only
  line item has `quantity` `1` and `unitPrice` `0` — sent with `?maxTotal=0`
  answers HTTP 201 with the ordinary created-order body.
- **G.** A request sent with `?maxTotal=-1` answers HTTP 400 with a JSON body whose
  keys are exactly `error`, `message` and `correlationId`, whose `error` is exactly
  `ValidationError`, whose `message` is a non-empty string and whose
  `correlationId` is a non-empty string.
- **H.** A request sent with `?maxTotal=` answers HTTP 400 with that same
  validation-error body.
- **I.** A request sent with `?maxTotal=abc` answers HTTP 400 with that same
  validation-error body.
- **J.** A request sent with `?maxTotal=NaN` answers HTTP 400 with that same
  validation-error body.
- **K.** A request sent with `?maxTotal=Infinity` answers HTTP 400 with that same
  validation-error body.
- **L.** A request sent with `?maxTotal=50&maxTotal=100` answers HTTP 400 with that
  same validation-error body, rather than applying either value.
- **M.** A request whose body fails the existing create-order input validation and
  whose `maxTotal` is not well formed answers HTTP 400 with that same
  validation-error body — the answer the invalid body already produces on its own.
  It is never HTTP 409 and never a successful creation.
- **N.** For one and the same request body, the line-item `subtotal` values and the
  `total` in a successful answer are the same numbers whether `maxTotal` is absent
  or present and not exceeded. No `subtotal` and no `total` the service reports
  changes, and `GET /health` answers exactly as it does today.
