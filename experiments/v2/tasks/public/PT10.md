## Objective

A caller finds out that the service will not accept an order only by trying to
place it and being refused. An integration that assembles an order over several
steps, or that wants to warn a user before committing, has no way to ask the
question in advance. Add the ability to ask whether a proposed order would be
accepted, and answer that question without placing one.

## User-visible behaviour

A `POST /orders/check` request carries the **existing create-order request body**
and answers with the service's verdict on it.

The request body is exactly the body `POST /orders` already takes: a JSON object
carrying `customerId` and `items`, where each entry of `items` carries
`productId`, `name`, `quantity` and `unitPrice`.

```json
{
  "customerId": "cust-1",
  "items": [
    { "productId": "p-100", "name": "Notebook", "quantity": 2, "unitPrice": 25 }
  ]
}
```

Every such request answers **HTTP 200** with a JSON body containing exactly one
key, `acceptable`, whose value is `true` or `false`:

```json
{
  "acceptable": true
}
```

- The body carries **no** other key: exactly that one, and no second.
- `acceptable` is a JSON boolean — `true` or `false` — and never a string, a
  number or `null`.

### What `acceptable` means

`acceptable` is `true` exactly when a `POST /orders` request carrying that same
body would be answered HTTP 201, and `false` exactly when such a request would be
answered HTTP 400.

The verdict therefore agrees with the answer the service already gives. This task
states **no** new rule about what the service accepts: it adds no input
requirement, removes none and relaxes none, and it requires **no** change to
`POST /orders`, which keeps its current behaviour, status codes and response
bodies exactly.

### The answer is a verdict, not an order

The answer carries none of the fields that identify a placed order: no `id`, no
`status`, no `createdAt`, no `customerId`, no `items` and no `total`. It carries
`acceptable` and nothing else.

### A proposed order the service would not accept

A request the service would refuse is **not** an error for this endpoint. Asking
about an order that would be refused is a perfectly ordinary question, and it is
answered HTTP 200 with `acceptable` `false` — never HTTP 400, never HTTP 422 and
never any other status code.

For example, the body

```json
{
  "customerId": "cust-1",
  "items": [
    { "productId": "p-100", "name": "Notebook", "quantity": 0, "unitPrice": 25 }
  ]
}
```

answers HTTP 200 with

```json
{
  "acceptable": false
}
```

### The cases this task fixes

For each body below, `POST /orders/check` answers HTTP 200 and the value of
`acceptable` is the one stated. Each value is the one the agreement above
requires, and each is also stated here directly so that no case is left to
inference.

| Proposed order | `acceptable` |
|---|---|
| a `customerId` that is a non-empty string, and an `items` array of one or more entries each carrying a non-empty `productId`, a non-empty `name`, a `quantity` that is a number greater than `0` and a `unitPrice` that is a number and is not negative | `true` |
| the same, but with a `unitPrice` of `0` | `true` |
| `customerId` absent | `false` |
| `customerId` present and empty | `false` |
| `items` absent | `false` |
| `items` present but not an array | `false` |
| `items` present and an empty array | `false` |
| an entry whose `productId` is absent, or present and empty | `false` |
| an entry whose `name` is absent, or present and empty | `false` |
| an entry whose `quantity` is `0`, is negative, or is not a number | `false` |
| an entry whose `unitPrice` is negative, or is not a number | `false` |
| more than one entry, where at least one of them is one of the unacceptable entries above | `false` |

### Asking twice

Asking the same question twice answers the same way: two `POST /orders/check`
requests carrying identical bodies answer with the same status code and the same
`acceptable` value, in either order and whatever else happened in between.

## Inputs and outputs

- Input: a JSON body of the shape `POST /orders` already takes.
- Output: HTTP 200 with a JSON body whose only key is `acceptable`, whose value is
  a JSON boolean.
- There is no rejection output. This endpoint answers HTTP 200 for every request
  body within this task's scope.

## Error behaviour

This task adds **no** error answer. `POST /orders/check` answers HTTP 200 for
every request body this task defines, and the fact that a proposed order would be
refused is reported as `acceptable` `false` rather than as an error. The existing
error behaviour of every other endpoint is unchanged.

## Out of scope

Everything below is **outside** this task. It states no required status code and
no required response body for any of it, and the service's existing handling of
such a request is unchanged.

- **A request body that is not a JSON object** — a JSON array, a JSON string, a
  JSON number, `true`, `false` or `null` as the whole body. No status code and no
  body is required for any of them.
- **An entry of `items` that is not a JSON object** — `null`, a number, a string
  or an array in the `items` array. Whether such a proposed order is acceptable is
  deliberately left undefined.
- **A `productId` or `name` that is present but consists only of whitespace.**
  Whether such a proposed order is acceptable is deliberately left undefined.
- **Extra keys.** A request body carrying keys beyond `customerId` and `items`,
  and an entry carrying keys beyond the four named above, are left undefined.
- **Every HTTP method other than `POST` on this path**, and every other path this
  task does not name.
- **Anything not visible in the answer to a single request.** Every requirement in
  this task is a status code and a JSON response body. It states nothing about
  what the service stores, or does not store, when the question is asked.
- **Transport-level and body-parsing rejections.** A body that cannot be parsed as
  JSON, a body that is too large, a request whose media type or charset is not
  supported, an aborted request, and every other transport-level rejection keep
  exactly the handling they have today.
- **Response headers.** No response header is part of this task's required
  behaviour. Any response header the service already sets keeps the behaviour it
  already has.
- **Log output.** Log output is not part of this task's required behaviour.
- **Other endpoints.** `GET /health` and `POST /orders` keep their current
  behaviour, status codes and response bodies, and `POST /orders` gains no new
  request field and no new query parameter.

## Functional completion criteria

Each criterion is decidable from the status code and the JSON body of the answers
to ordinary HTTP requests.

- **A.** A `POST /orders/check` request carrying a proposed order of the first
  kind in the table answers HTTP 200 with a JSON body whose key set is exactly
  `acceptable` and whose `acceptable` is the boolean `true`.
- **B.** A `POST /orders/check` request carrying each of the unacceptable proposed
  orders in the table answers HTTP 200 with that same one-key body and
  `acceptable` the boolean `false`.
- **C.** For every proposed order in the table, the verdict agrees with the
  service's own answer to `POST /orders` for the same body: `acceptable` is `true`
  exactly for those the service answers HTTP 201, and `false` exactly for those it
  answers HTTP 400.
- **D.** A proposed order whose only entry has a `unitPrice` of `0` and a
  `quantity` greater than `0` answers `acceptable` `true`, so a zero price is not
  treated as a refusal.
- **E.** No answer to `POST /orders/check` carries `id`, `status`, `createdAt`,
  `customerId`, `items`, `total`, `error`, `message` or `correlationId`.
- **F.** Two `POST /orders/check` requests carrying identical bodies answer with
  the same status code and the same `acceptable` value.
- **G.** `POST /orders` answers exactly as it does today — the same status codes,
  the same response bodies and the same values — and `GET /health` answers exactly
  as it does today.
