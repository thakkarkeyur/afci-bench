## Objective

The service can create orders but cannot yet return an individual order that was
created earlier. Add the ability to fetch one previously created order by its
identifier.

## User-visible behaviour

A `GET /orders/{id}` request returns the stored order whose identifier matches
`{id}`. The returned JSON has exactly the same keys as the order returned when it
was first created: `id`, `customerId`, `items`, `total`, `status` and
`createdAt`, where each element of `items` has `productId`, `name`, `quantity`,
`unitPrice` and `subtotal`.

## Inputs and outputs

- Input: the order identifier, taken from the URL path.
- Success output: HTTP 200 with the order as a JSON body, using the keys listed
  above.

## Error behaviour

If no order exists for the given identifier, respond with HTTP 404 and the
service's existing error JSON body:

```json
{
  "error": "NotFoundError",
  "message": "<non-empty human-readable message>",
  "correlationId": "<the request's correlation identifier>"
}
```

- `error` for a missing order is exactly `NotFoundError`.
- `message` is free text and only has to be a non-empty string.
- `correlationId` keeps the behaviour it already has for order creation: the
  value supplied with the request if there is one, otherwise a generated
  non-empty value.

## Constraints

- The values returned for a fetched order (line-item subtotals and the overall
  total) must equal the values that were computed when that order was created; do
  not recompute them to a different result.
- Existing endpoints keep their current behaviour and responses unchanged.

## Functional completion criteria

- Creating an order and then requesting it by its returned identifier yields that
  same order, with matching totals and the keys listed above.
- Requesting an identifier that does not exist yields HTTP 404 with `error`
  exactly `NotFoundError` and a non-empty `message`.

## Validation

Run `npm run ci:agent`; it must pass.
