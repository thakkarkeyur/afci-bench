## Objective

`POST /orders` already rejects an order-creation request whose input does not
satisfy its existing input validation, and answers it with a JSON error body. A
request whose body is not parseable JSON is also rejected, but it is not answered
with that JSON error body at all. Make these two kinds of rejected
order-creation request answer with the same error body.

## Scope

This task covers exactly two kinds of rejected `POST /orders` request, and no
others:

1. **A semantic input-validation failure** — the request body was parsed as JSON
   and then failed the existing input validation.
2. **A JSON parse failure** — the request body is not parseable JSON, and the
   request carries the header `Content-Type: application/json`.

Every other way a `POST /orders` request can fail is outside the scope of this
task and keeps its current status code and its current response body exactly as
they are today. That includes a payload-too-large rejection such as one answered
HTTP 413 today, an unsupported-media-type or unsupported-charset rejection such
as one answered HTTP 415 today, an aborted request, and any other transport-level
or body-parsing rejection. None of them has to answer HTTP 400, none of them has
to carry `error` `ValidationError`, and none of them has to carry the JSON object
below.

## User-visible behaviour

Each of the two kinds named in **Scope** answers with HTTP 400, a `Content-Type`
response header whose media type is `application/json`, and this JSON object:

```json
{
  "error": "ValidationError",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- The response carries a `Content-Type` header whose media type begins with
  `application/json`. A parameter such as `; charset=utf-8` may follow it.
- `error` is exactly the string `ValidationError`.
- `message` is a non-empty string. Its exact wording is not part of the required
  behaviour; any non-empty string satisfies it.
- `correlationId` is a non-empty string.
- No response header other than `Content-Type` is part of this task's required
  behaviour. Any response header the service already sets keeps the behaviour it
  already has.

Each of the two kinds named in **Scope** is detailed below.

1. **A semantic input-validation failure.** Examples that are already meaningful
   for the current create-order input:
   - `customerId` present but empty (`""`), with an otherwise valid `items`
     entry;
   - `items` present but empty (`[]`), with an otherwise valid `customerId`;
   - an `items` entry whose `quantity` is not a positive number, for example
     `0`.

   Each of these already answers HTTP 400 with `error` exactly `ValidationError`
   and an `application/json` response media type today, and keeps doing so.

2. **A JSON parse failure**, sent with the request header
   `Content-Type: application/json` — for example the body
   `{"customerId": "cust-1", "items": [`. Today such a request answers HTTP 400
   but **not** with the JSON object above and **not** with an `application/json`
   response media type. It must answer with that same JSON object and that same
   response media type: `error` exactly `ValidationError`, a non-empty `message`,
   and a non-empty `correlationId`.

## Inputs and outputs

- Input: the existing create-order request body, or a body that is not parseable
  JSON.
- Output on either of the two kinds named in **Scope**: HTTP 400, a
  `Content-Type` response header whose media type begins with `application/json`,
  and the JSON object above. That response body is JSON — never HTML, never
  empty.
- Output on success: unchanged. A valid create-order request still answers HTTP
  201 with the existing create-order response body and its existing values.

## Error behaviour

- One shape covers the two kinds named in **Scope**: the same three keys, the
  same `error` value, the same HTTP status and the same response media type.
- `correlationId` keeps the behaviour it already has: the value supplied with the
  request when one is supplied, otherwise a generated non-empty value.
- No further required key is added to that rejection body, and none is removed.

## Constraints

- No new endpoint and no new request field is required.
- Successful order creation and `GET /health` keep their current behaviour,
  status codes and response bodies.
- Nothing outside the two kinds of rejected `POST /orders` request named in
  **Scope** has to change.

## Functional completion criteria

- A `POST /orders` request whose parsed body fails the existing input validation
  answers HTTP 400, carries a `Content-Type` response header whose media type
  begins with `application/json`, and carries a JSON body whose `error` is
  exactly `ValidationError`, whose `message` is a non-empty string, and whose
  `correlationId` is a non-empty string. This holds at least for an empty
  `customerId`, for an empty `items` array, and for an `items` entry with a
  non-positive `quantity`.
- A `POST /orders` request whose body is not parseable JSON, sent with
  `Content-Type: application/json`, answers HTTP 400, carries a `Content-Type`
  response header whose media type begins with `application/json`, and carries a
  JSON body with those same three keys, the same `error` value `ValidationError`,
  a non-empty `message` and a non-empty `correlationId`.
- Those two responses have the same status code, the same response media type and
  the same body shape as each other.
- No response header other than `Content-Type` has to change or has to carry a
  particular value.
- A `POST /orders` request that fails in any way outside **Scope** — for example
  one answered HTTP 413 or HTTP 415 today — still answers exactly as it does
  today.
- A valid create-order request still answers HTTP 201 with an unchanged response
  body.
