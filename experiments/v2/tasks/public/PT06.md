## Objective

`POST /orders` already rejects an order-creation request whose input does not
satisfy its existing input validation, and answers it with a JSON error body. A
request whose body cannot be parsed as JSON is also rejected, but it is not
answered with that JSON error body at all. Make both kinds of rejected
order-creation request answer with the same error body.

## User-visible behaviour

A rejected `POST /orders` request answers with HTTP 400 and this JSON object:

```json
{
  "error": "ValidationError",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- `error` is exactly the string `ValidationError`.
- `message` is a non-empty string. Its exact wording is not part of the required
  behaviour; any non-empty string satisfies it.
- `correlationId` is a non-empty string.

Both of the following are rejected requests, and both answer exactly that way.

1. **A request that fails the existing input validation.** Examples that are
   already meaningful for the current create-order input:
   - `customerId` present but empty (`""`), with an otherwise valid `items`
     entry;
   - `items` present but empty (`[]`), with an otherwise valid `customerId`;
   - an `items` entry whose `quantity` is not a positive number, for example
     `0`.

   Each of these already answers HTTP 400 with `error` exactly `ValidationError`
   today, and keeps doing so.

2. **A request whose body is not parseable JSON**, sent with the request header
   `Content-Type: application/json` — for example the body
   `{"customerId": "cust-1", "items": [`. Today such a request answers HTTP 400
   but **not** with the JSON object above. It must answer with that same JSON
   object: `error` exactly `ValidationError`, a non-empty `message`, and a
   non-empty `correlationId`.

## Inputs and outputs

- Input: the existing create-order request body, or a body that cannot be parsed
  as JSON.
- Output on rejection: HTTP 400 and the JSON object above. The response body is
  JSON — never HTML, never empty.
- Output on success: unchanged. A valid create-order request still answers HTTP
  201 with the existing create-order response body and its existing values.

## Error behaviour

- One shape covers both kinds of rejection: the same three keys, the same `error`
  value, and the same HTTP status.
- `correlationId` keeps the behaviour it already has: the value supplied with the
  request when one is supplied, otherwise a generated non-empty value.
- No further required key is added to the rejection body, and none is removed.

## Constraints

- No new endpoint and no new request field is required.
- Successful order creation and `GET /health` keep their current behaviour,
  status codes and response bodies.
- Nothing beyond the rejection response of `POST /orders` has to change.

## Functional completion criteria

- An order-creation request that fails the existing input validation answers HTTP
  400 with a JSON body whose `error` is exactly `ValidationError`, whose
  `message` is a non-empty string, and whose `correlationId` is a non-empty
  string. This holds at least for an empty `customerId`, for an empty `items`
  array, and for an `items` entry with a non-positive `quantity`.
- An order-creation request whose body is not parseable JSON, sent with
  `Content-Type: application/json`, answers HTTP 400 with a JSON body carrying
  those same three keys, the same `error` value `ValidationError`, a non-empty
  `message` and a non-empty `correlationId`.
- The two rejection responses above have the same shape as each other.
- A valid create-order request still answers HTTP 201 with an unchanged response
  body.

## Validation

Run `npm run ci:agent`; it must pass.
