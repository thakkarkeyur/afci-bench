## Objective

`POST /orders` does not report all of its failures the same way. A failure that is
not caused by invalid input is currently reported to the caller as though the
input had been invalid, and a request whose body cannot be parsed as JSON is not
answered with the service's error JSON body at all. Make every order-creation
failure answer with the same error envelope and the correct status code.

## User-visible behaviour

Every `POST /orders` failure answers with the service's existing error JSON body:
the documented keys `error` and `message`, both non-empty strings, alongside the
`correlationId` key the service already returns.

```json
{
  "error": "ValidationError",
  "message": "<non-empty human-readable message>",
  "correlationId": "<the request's correlation identifier>"
}
```

- A request rejected because its input is invalid returns HTTP 400 with `error`
  exactly `ValidationError`. This includes a body that is not valid JSON, a
  missing or empty `customerId`, an empty `items` array, and an item with a
  missing `productId` or `name`, a `quantity` that is not a positive number, or a
  negative `unitPrice`.
- A request that fails for a reason that is not invalid input — for example a
  failure raised while the order is being stored — returns HTTP 500 with `error`
  exactly `InternalServerError`. Such a failure must not be answered with HTTP 400
  and must not be answered with `error` `ValidationError`.
- Successful order creation is unchanged: HTTP 201 with the existing order
  response body.
- No new endpoint and no new request field is required.

## Inputs and outputs

- Input: the existing create-order request.
- Output: on success, the existing create-order response. On failure, the error
  JSON body above, with the status code and the `error` value stated for that kind
  of failure.

## Error behaviour

- `message` is free text and only has to be a non-empty string; it is never empty
  or absent.
- `correlationId` keeps the behaviour it already has: the value supplied with the
  request if there is one, otherwise a generated non-empty value.
- Every failure response is JSON — never HTML, never an empty body.

## Constraints

- The same three keys appear on every order-creation failure response; do not
  introduce a second, differently shaped failure body.
- Successful responses and their status codes are unchanged.
- Endpoints other than `POST /orders` keep their current behaviour and responses
  unchanged.

## Functional completion criteria

- Invalid input returns HTTP 400 with `error` exactly `ValidationError` and a
  non-empty `message`.
- A request body that is not valid JSON returns HTTP 400, as JSON, with `error`
  exactly `ValidationError` and a non-empty `message`.
- A failure that is not caused by invalid input returns HTTP 500 with `error`
  exactly `InternalServerError` and a non-empty `message`.
- Successful order creation still returns HTTP 201 with an unchanged response
  body.

## Validation

Run `npm run ci:agent`; it must pass.
