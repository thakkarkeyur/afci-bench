## Objective

A caller can place an order, but has no way to find out what a set of line items
would cost before committing to one. Add the ability to price a proposed set of
line items and answer with that pricing.

## User-visible behaviour

A `POST /orders/preview` request carries a proposed set of line items and answers
with the price of each one and the price of the whole set.

The request body contains exactly one key, `items`, whose value is an array. Each
entry of `items` contains exactly `productId`, `name`, `quantity` and
`unitPrice`. There is no `customerId` in this request.

```json
{
  "items": [
    { "productId": "p-100", "name": "Notebook", "quantity": 3, "unitPrice": 15.33 },
    { "productId": "p-200", "name": "Sketchbook", "quantity": 1, "unitPrice": 15.33 }
  ]
}
```

A valid request answers HTTP 200 with a JSON body containing exactly `items` and
`total`. Each entry of the answer's `items` contains exactly `productId`, `name`,
`quantity`, `unitPrice` and `subtotal`:

```json
{
  "items": [
    { "productId": "p-100", "name": "Notebook", "quantity": 3, "unitPrice": 15.33, "subtotal": 45.99 },
    { "productId": "p-200", "name": "Sketchbook", "quantity": 1, "unitPrice": 15.33, "subtotal": 15.33 }
  ],
  "total": 61.32
}
```

The answer is a price quotation, so it carries none of the fields that identify a
placed order: no `id`, no `status`, no `createdAt` and no `customerId`.

### An empty set of line items

An empty `items` array is a valid request. The request body

```json
{
  "items": []
}
```

answers HTTP 200 with

```json
{
  "items": [],
  "total": 0
}
```

### The prices agree with the ones order creation reports

For a valid non-empty set of line items, the item subtotals and the `total` this
request answers with are the same numeric values the service reports for those
same line items when they are submitted through the existing order-creation
operation.

This task introduces **no** new rounding rule and **no** new monetary-precision
rule, and requires **no** change to the prices the service already reports for an
order it has created.

## Inputs and outputs

- Input: a JSON body whose only key is `items`, as described above.
- Success output: HTTP 200 with a JSON body whose only keys are `items` and
  `total`, where each entry of `items` carries exactly `productId`, `name`,
  `quantity`, `unitPrice` and `subtotal`.
- Rejection output: HTTP 400 with the JSON body described under **Error
  behaviour**.

## Error behaviour

A `POST /orders/preview` request is rejected with HTTP 400 when any of the
following holds:

- `items` is absent;
- `items` is not an array;
- an entry has an absent or empty `productId`;
- an entry has an absent or empty `name`;
- an entry's `quantity` is not a number greater than `0`;
- an entry's `unitPrice` is not a number;
- an entry's `unitPrice` is negative.

Each of those answers carries a JSON body containing exactly:

```json
{
  "error": "ValidationError",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- `error` is exactly the string `ValidationError`.
- `message` is a non-empty string. Its exact wording is not part of the required
  behaviour; any non-empty string satisfies it.
- `correlationId` is a non-empty string.

## Constraints

- A body that cannot be parsed as JSON, a body that is too large, a request whose
  media type or charset is not supported, and every other transport-level or
  body-parsing rejection are **outside** this task. It states no required status
  code and no required body for any of them, and the service's existing handling
  of such a request is unchanged.
- No response header is part of this task's required behaviour.
- Log output is not part of this task's required behaviour.
- `GET /health` keeps its current behaviour, status code and response body.
- `POST /orders` keeps its current behaviour, status codes and response bodies,
  and gains no new request field.

## Functional completion criteria

- A `POST /orders/preview` request whose `items` array holds valid entries
  answers HTTP 200 with a JSON body whose keys are exactly `items` and `total`,
  where every entry of `items` carries exactly `productId`, `name`, `quantity`,
  `unitPrice` and `subtotal`, and where the body carries no `id`, no `status`, no
  `createdAt` and no `customerId`.
- For the same line items, those subtotals and that `total` equal the values the
  service reports for them through the existing order-creation operation.
- A request whose `items` array is empty answers HTTP 200 with an empty `items`
  array and a `total` of `0`.
- Each of the seven rejected cases listed under **Error behaviour** answers HTTP
  400 with a JSON body whose keys are exactly `error`, `message` and
  `correlationId`, whose `error` is exactly `ValidationError`, whose `message` is
  a non-empty string, and whose `correlationId` is a non-empty string.
- `GET /health` and `POST /orders` answer exactly as they do today.
