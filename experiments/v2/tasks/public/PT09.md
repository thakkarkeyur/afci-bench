## Objective

`POST /orders` is all-or-nothing: one line item the service will not accept
refuses the whole request, and the caller is told only that the request was
invalid. A caller assembling a basket from a catalogue it does not fully control
would rather have the order placed for the line items that are fine and be told
which ones were left out. Let a caller ask for that, and answer with the order
that was actually created and the positions of the line items it left out.

## User-visible behaviour

`POST /orders` gains one **optional query parameter**, `onUnacceptableItem`.
Nothing else about the request changes: the request body stays exactly the
existing create-order request body, this task adds **no** request-body field, and
it adds **no** request header.

Throughout this section the worked example is the existing create-order request
body

```json
{
  "customerId": "cust-1",
  "items": [
    { "productId": "p-100", "name": "Notebook", "quantity": 2, "unitPrice": 25 },
    { "productId": "",      "name": "Sketchbook", "quantity": 1, "unitPrice": 10 },
    { "productId": "p-300", "name": "Pencil", "quantity": 4, "unitPrice": 1.5 }
  ]
}
```

whose second entry carries an empty `productId`, and for which the service today
answers HTTP 400.

### 1. What makes a line item acceptable

An entry of `items` is **acceptable** when a `POST /orders` request that carries

- **no** `onUnacceptableItem`,
- the same `customerId`, and
- an `items` array holding **only that entry**

is answered HTTP 201. An entry that such a request does not answer HTTP 201 is
**unacceptable**.

This task states **no** new rule about what the service accepts. Acceptability is
read off the answer the service already gives; the service's existing input
requirements are unchanged, and nothing here adds one, removes one or relaxes
one.

In the worked example the first and third entries are acceptable and the second
is not.

### 2. A well-formed `onUnacceptableItem`

`onUnacceptableItem` is **well formed** when its value is exactly `reject` or
exactly `omit`, in lower case. No other value is well formed.

### 3. `onUnacceptableItem` is absent, or is `reject`

A `POST /orders` request that carries no `onUnacceptableItem`, and one that
carries `onUnacceptableItem=reject`, behave exactly as the request behaves today —
the same status codes, the same response bodies and the same values. In
particular the worked example answers HTTP 400 in both cases, and no answer
carries an `omitted` key.

### 4. `onUnacceptableItem=omit`

The order is created from the acceptable entries of `items` only, and the
unacceptable ones are left out.

A valid such request answers HTTP 201 with the body `POST /orders` already
answers a successful creation with, plus exactly **one** additional key,
`omitted`:

- `omitted` is an array of the positions, counting from `0`, that the
  unacceptable entries occupied in the submitted `items` array, in ascending
  order.
- `omitted` is present on **every** HTTP 201 answer to a request carrying
  `onUnacceptableItem=omit`, and is an empty array when no entry was left out.
- The answer's `items` and `total` describe the **retained** entries only. The
  order is the order the service created, so its `items`, its `total` and every
  other field it reports are the ones the service reports for exactly those
  retained entries.

The worked example sent with `?onUnacceptableItem=omit` answers HTTP 201 with
`omitted` equal to `[1]`, and with `items` and `total` describing its first and
third entries only.

### 5. `onUnacceptableItem=omit` when nothing is acceptable

When `onUnacceptableItem` is `omit` and **every** entry of `items` is
unacceptable, the request answers HTTP 422 with a JSON body containing exactly:

```json
{
  "error": "NoAcceptableLineItems",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- `error` is exactly the string `NoAcceptableLineItems`.
- `message` is a non-empty string. Its exact wording is not part of the required
  behaviour; any non-empty string satisfies it.
- `correlationId` is a non-empty string. This task fixes no further requirement
  on its value.
- The body carries **no** other key: exactly those three, and no fourth.

That answer is **not** interchangeable with a rejection for invalid input: it is
answered HTTP 422 with `error` exactly `NoAcceptableLineItems` — never HTTP 400,
and never `error` `ValidationError`.

### 6. An `onUnacceptableItem` that is not well formed

Each of the following answers HTTP 400 with the JSON body `POST /orders` already
answers a rejected create-order request with, containing exactly:

```json
{
  "error": "ValidationError",
  "message": "<non-empty string>",
  "correlationId": "<non-empty string>"
}
```

- a value that is neither exactly `reject` nor exactly `omit` — for example
  `skip`, `drop`, `Omit`, `OMIT`, `true`;
- an **empty** value: `?onUnacceptableItem=` carries a parameter that is present
  and empty, and an empty value is **not** an absent parameter;
- the parameter given **more than once** — for example
  `?onUnacceptableItem=omit&onUnacceptableItem=reject`. Such a request is
  ambiguous and is answered as invalid; one of the repeated values must **never**
  be silently chosen and applied.

`error` is exactly the string `ValidationError`, `message` is a non-empty string
whose wording is not part of the required behaviour, and `correlationId` is a
non-empty string. This is the existing rejection body, reused unchanged. This
task introduces **no** second rejection shape for invalid input, adds no key to
that body and removes none.

### 7. The answers that stay exactly as they are

Whatever `onUnacceptableItem` is, a `POST /orders` request answers HTTP 400 with
the existing validation-error body when

- `customerId` is absent or empty; or
- `items` is absent; or
- `items` is not an array; or
- `items` is an empty array.

An empty `items` array carries no unacceptable entry, so it is **never** answered
HTTP 422; it keeps the answer it has today. The same holds for a request whose
`customerId` the service does not accept: it is answered exactly as it is today,
whatever its line items are.

### 8. The order the answers are decided in

For one and the same request, exactly one of the answers above applies, decided
in this order:

1. `onUnacceptableItem` is present and not well formed → HTTP 400 with the
   existing validation-error body.
2. Otherwise `customerId` is absent or empty, or `items` is absent, not an array,
   or empty → HTTP 400 with the existing validation-error body, exactly as today.
3. Otherwise `onUnacceptableItem` is absent or `reject` → exactly today's
   behaviour.
4. Otherwise every entry of `items` is unacceptable → HTTP 422 with the
   `NoAcceptableLineItems` body.
5. Otherwise → HTTP 201 with the created-order body plus `omitted`.

### No new monetary rules

The retained entries are priced exactly as the service prices them today. This
task introduces **no** new rounding rule, **no** new monetary-precision rule,
**no** discount rule and **no** currency conversion, and it changes **no**
line-item `subtotal` and **no** order `total` the service reports for any set of
line items it creates an order from.

## Inputs and outputs

- Input: the existing create-order request body, plus the optional query
  parameter `onUnacceptableItem`.
- Output when the parameter is absent or `reject`: the existing answer,
  unchanged.
- Output when the parameter is `omit` and at least one entry is acceptable: HTTP
  201 with the existing created-order body plus `omitted`.
- Output when the parameter is `omit` and no entry is acceptable: HTTP 422 with a
  JSON body whose keys are exactly `error`, `message` and `correlationId`, and
  whose `error` is exactly `NoAcceptableLineItems`.
- Output when the parameter is present and not well formed, or is given more than
  once: HTTP 400 with the existing validation-error body, whose `error` is
  exactly `ValidationError`.

## Error behaviour

- Two answers, and only two, are added by this task: HTTP 422 with `error`
  `NoAcceptableLineItems` when omission leaves nothing to create an order from,
  and the existing HTTP 400 `ValidationError` body for an `onUnacceptableItem`
  that is not well formed or is repeated.
- The two are never confused: an ill-formed or repeated `onUnacceptableItem` is
  never answered HTTP 422, and a request whose entries are all unacceptable under
  `omit` is never answered HTTP 400.
- No existing rejection of `POST /orders` gains a new status code or a new body.

## Out of scope

Everything below is **outside** this task. It states no required status code and
no required response body for any of it, and the service's existing handling of
such a request is unchanged.

- **An entry of `items` that is not a JSON object** — `null`, a number, a string
  or an array in the `items` array. Its treatment, and whether it counts as
  acceptable or unacceptable, is deliberately left undefined.
- **A `productId` or `name` that is present but consists only of whitespace.**
  Whether such an entry is acceptable is deliberately left undefined, and no
  answer is required for a request that carries one.
- **Spellings of `onUnacceptableItem` this task does not define.** The key written
  with no value part at all, as in `?onUnacceptableItem`; any bracketed or
  structured spelling of the key, as in `?onUnacceptableItem[]=omit`; and a value
  carrying leading or trailing whitespace, percent-encoded or otherwise. None of
  them is one of the cases in sections 2, 3, 4, 5 and 6, and where such a spelling
  could also be read as falling under section 6, this list governs.
- **Anything not visible in the answer to a single request.** Every requirement
  in this task is a status code and a JSON response body. It states nothing about
  what the service stores, or does not store, for any request — including which
  line items it stores for a request answered HTTP 201 under `omit`.
- **Transport-level and body-parsing rejections.** A body that cannot be parsed
  as JSON, a body that is too large, a request whose media type or charset is not
  supported, an aborted request, and every other transport-level rejection keep
  exactly the handling they have today.
- **Response headers.** No response header is part of this task's required
  behaviour. Any response header the service already sets keeps the behaviour it
  already has.
- **Log output.** Log output is not part of this task's required behaviour.
- **Other endpoints.** `GET /health` keeps its current behaviour, status code and
  response body. No other endpoint is added or changed.

## Functional completion criteria

Each criterion is decidable from the status code and the JSON body of the answers
to ordinary HTTP requests.

- **A.** A valid request with no `onUnacceptableItem` answers HTTP 201 with the
  existing created-order response body and the existing values, exactly as it does
  today, and its body carries no `omitted` key.
- **B.** The worked example sent with no `onUnacceptableItem`, and the worked
  example sent with `?onUnacceptableItem=reject`, both answer HTTP 400 with a JSON
  body whose keys are exactly `error`, `message` and `correlationId` and whose
  `error` is exactly `ValidationError`.
- **C.** The worked example sent with `?onUnacceptableItem=omit` answers HTTP 201
  with a body whose `omitted` is exactly `[1]`.
- **D.** For that same answer, `items` and `total` are the ones the service
  reports for a request whose `items` array holds the worked example's first and
  third entries only — the same number of entries, the same per-entry values and
  the same `total`.
- **E.** A request all of whose entries are acceptable, sent with
  `?onUnacceptableItem=omit`, answers HTTP 201 with `omitted` equal to `[]`, and
  with the same `items` values and the same `total` as the same body sent with no
  `onUnacceptableItem`.
- **F.** A request whose entries are all unacceptable, sent with
  `?onUnacceptableItem=omit`, answers HTTP 422 with a JSON body whose keys are
  exactly `error`, `message` and `correlationId`, whose `error` is exactly
  `NoAcceptableLineItems`, whose `message` is a non-empty string and whose
  `correlationId` is a non-empty string.
- **G.** A request whose `items` array is empty answers HTTP 400 with the
  validation-error body whether `onUnacceptableItem` is absent, `reject` or
  `omit` — never HTTP 422 and never HTTP 201.
- **H.** A request whose `customerId` is empty answers HTTP 400 with the
  validation-error body whether `onUnacceptableItem` is absent, `reject` or
  `omit`, and whatever its line items are.
- **I.** A request sent with `?onUnacceptableItem=skip` answers HTTP 400 with the
  validation-error body, and so does one sent with `?onUnacceptableItem=Omit`.
- **J.** A request sent with `?onUnacceptableItem=` answers HTTP 400 with that
  same validation-error body.
- **K.** A request sent with
  `?onUnacceptableItem=omit&onUnacceptableItem=reject` answers HTTP 400 with that
  same validation-error body, rather than applying either value.
- **L.** For one and the same set of acceptable line items, the line-item
  `subtotal` values and the `total` in a successful answer are the same numbers
  whether they were submitted on their own with no `onUnacceptableItem` or
  retained out of a larger `items` array under `omit`. No `subtotal` and no
  `total` the service reports changes, and `GET /health` answers exactly as it
  does today.
